# O.R.C.A. UI 与文案改进规格

日期：2026-09-07。配套 [审计报告](2026-09-07-v3.0.1-audit.md)。本文件是下一轮的修复依据，**不是已经完成的设计稿或修改说明**。

目标很简单：先让所有东西放对、点得到，再让界面和回答更简洁。Classic 保留旧版蓝白外观，Modern 单独优化，不能为了统一而再次改坏 Classic。

## 1. 先修布局，不再叠补丁

### 顶栏与侧栏

已确认 Modern 顶栏占位冲突：实际 76px，父 grid 留 46px。侧栏“新建会话”上半部和正文顶部被遮挡。底部 30px 状态栏又压住“设置”。

建议实现：

- 顶栏尺寸只定义一次，窗口壳与 grid 行引用同一变量；Classic 和 Modern 分别定义自己的尺寸。
- 状态栏应有真实布局槽位。若保留悬浮定位，侧栏与正文必须同步预留它的高度，但优先选普通布局。
- 顶栏只有 `文件 / 项目 / 工具 / 设置` 四个入口；第二行放 O.R.C.A.、当前工作区/会话与必要动作。不再加重复品牌条。
- 模型选择以 Composer 为主，顶部和底栏不必再次重复相同模型信息。是否移除辅助位置应在对比稿中呈现，不悄悄删功能。
- 侧栏项目列表独立滚动，底部入口始终能点击；不要靠固定一个大 padding 掩盖窗口高度问题。

验收不仅看截图：用 `elementFromPoint` 检查按钮中心命中自身；顶栏 bottom 必须等于下一行 top；菜单打开、收起侧栏和面板后重复测量。

### Composer

保留已确定的 Modern 单行顺序：

```text
+  权限                 [运行状态]   模型  思考强度  [暂停] [发送/停止]
```

- 模型和思考强度是轻量文字入口，不增加外层卡片、胶囊或厚边框。
- 发送/停止共用固定槽位；暂停仅运行时显示。模型名和状态可以省略，按钮不能缩成窄条。
- 正常窗口下模型、思考强度、按钮垂直居中。窄容器先缩短状态与模型名，再收纳低频内容，不挤占停止。
- 760px 以上当前矩阵这部分没有重叠，保留现有成功行为。360px 压力场景仍有模型/思考和暂停/停止交叠，不能宣称已支持所有窄尺寸。
- 输入框只提示输入，不同时塞三套快捷语法；快捷用法放到添加菜单或按需帮助中。
- 权限名称清楚区分“询问”“自动审批”“完全访问”，保留现有安全规则和必要警告。简化文案不等于弱化授权。

### Classic

- 使用 `desktop-v2.1.3` 的 DOM/CSS 与相同 fixture 做对照，不把“差不多蓝白”当完成。
- 修复搜索与面板开关的相交区域；浏览器预览控件和实际原生标题栏分别验收。
- 保留旧版 Composer 控件位置、侧栏宽度、字体层级、按钮形状和过程展示密度；品牌只替换为 O.R.C.A.。
- 将当前作用于两种样式的后追加 `.composer-*` / `.app-chrome-*` 规则逐条归属到对应样式。先按已复现的冲突范围整理，不做与本轮无关的大规模重写。
- 样式切换仍保留重启提示，不能在当前窗口临时伪装另一种窗口装饰。

## 2. Modern 的视觉调整

本轮实际渲染仍有蓝灰块、带阴影的用户气泡、整行边框包裹的过程框，以及底栏多个低频指标。可点击性问题修好后，再做这些局部调整：

| 部位 | 调整方向 | 保留的功能 |
|---|---|---|
| 页面 | 冷白正文、轻灰侧栏、深灰文字，蓝色只用于选中和主要状态 | 清晰的当前项目/会话定位 |
| 过程 | 摘要行优先，完成后折叠；无内容时不撑一个大框 | 工具、命令、输出、思考和错误详情可展开 |
| 用户消息 | 减少阴影和大面积色块，保持与答案的可辨识差异 | 附件、复制、引用 |
| 状态栏 | 默认只保留当前任务真正有用的状态；缓存命中、阈值等放详情 | 可靠的上下文/费用数据仍可查看，未知数据不伪造为零 |
| 设置 | 先显示值与可执行动作，简短提示紧跟相关字段 | 诊断详情、配置语法和高级选项按需展开 |
| 错误 | 说明发生了什么、数据是否保留、能做什么 | 可展开技术错误与复制诊断，不直接覆盖整个应用 |

不应照抄某个产品的全部布局。参考 Codex 的信息密度与层级，而不是复制装饰。默认字体不随视口缩放；名称过长时合理省略并提供完整 tooltip。不要把提高可读性变成给所有区域加粗、放大或增加一层卡片。

## 4. 模型回答与进度话术

### 真实样本

输入：“你好，我想用这个软件整理读书笔记，可以怎么开始？”

CLI 默认 profile 实际先查系统与目录，其中 `ls -la` 在 cmd 下失败又改用 `dir /a`，再发 ask，最后给出长篇模板。4 次请求耗时约 32 秒。这个问题本来不需要读取磁盘。

更合适的起始回答示例：

> 先发一段摘录或已有笔记给我，我可以帮你整理成“要点、摘录、你的想法”。每本书保留一份 Markdown 笔记，后面再加书目索引。你现在想整理哪本书？

这不是所有回答都要套用的固定模板。用户要求完整模板、目录规划或实际创建时，再提供相应细节。

### 提示词的改动范围

| 源码 | 当前倾向 | 改进原则 |
|---|---|---|
| `internal/promptprofile/enhanced.go:16-22,160-179` | 多个 profile 共用工具前说明、阶段更新、结果/验证/阻塞的 completion contract | 根据任务需要决定是否播报；单次查询不硬套项目交付流程；耗时任务只报告真正的新进展 |
| `internal/promptprofile/enhanced.go:234-241` | step thinking 打开后含探索、2–3 方案、设计、计划、评审等固定阶段 | 仅复杂修改需要完整流程；简单解释/咨询不因开关就扩展成多阶段工程；不暴露内部思考过程 |
| `internal/config/config.go:1059-1091`、`internal/boot/boot.go:292-298` | 默认 coding profile 倾向用工具核实工作区 | 先区分“询问怎么做”和“要求动手做”；不依赖本地事实的咨询直接回答。既有 simple answers 不强制 todo 的规则应保留并加强行为测试 |

约束：

- 不强制每个最终回答都分“结果/实现/验证/风险/下一步”。做了实际修改时才交代修改和验证；没有做过的测试不能写成通过。
- 不为展示过程而连续发送“正在分析、正在整理、正在准备”。只有状态变化或值得用户知道的进展才更新。
- 不反复说“安全、稳妥、零风险、完整闭环”等空泛承诺。具体说明会改什么、保留什么；无法保证就说未验证。
- 不因追求简短省略必要的权限询问、失败原因、外部发送对象或价格不确定性。
- 不以固定的长度/标题数代替理解用户。复杂审计、设计与文档可以很详细，普通问答不需要同样的外观。

## 5. 异常页面要可恢复

修复报告 F01/F14/F16 时一起整理话术与交互：

1. 首次加载失败：显示“设置未能加载”，提供重试和关闭，不永久显示加载中。
2. 刷新失败：保留当前数据，在相关区域显示提示，不清空选择。
3. 操作失败：只让该操作结束，恢复按钮可用；不触发全局崩溃覆盖层。
4. 需要配置模型：保留草稿，显示明确入口，不默默丢掉发送内容。
5. 无法判断当前能力：写“尚未检测”或“检测失败”，不假装成功、没有显卡或没有费用。

## 6. 对比与验收

必须保留 Modern/Classic 两份对比，不重命名为含旧品牌的产品。验收材料使用合成项目、长模型名和长会话标题，不放真实密钥或用户私有对话。

| 维度 | 必测内容 |
|---|---|
| 尺寸 | 760/820/1024/1366/1920；320–580 仅作为窄容器压力范围单列 |
| 状态 | 新会话、草稿、运行、暂停、停止、审批、错误、完成过程展开/收起 |
| 布局 | 侧栏/右面板开关、菜单展开、顶部与底部占位、按钮真实命中、横向溢出 |
| 语言 | 中文/英文和长标签；无逐字换行、错误省略或被背景遮住 |
| 焦点 | 键盘菜单、弹窗焦点不逃逸、关闭后焦点返回、Esc 行为 |
| 原生 | 两种窗口装饰、系统 DPI、最大化/还原、跨显示器；不能用浏览器 DPR 替代 |
| 回答 | 问候、定义解释、读书/写作咨询、单次查询、实际代码修改、多文件调试；逐项评估工具是否必要、内容是否充分、是否无根据地宣称完成 |

回答行为至少在 coding/assistant/Orca 三个 profile 下对照，step thinking 分开测试。先用 fixture 保证工具和状态契约，再用少量真实调用评估表达；单次样本不能作为模型优劣排名。

完成标准：没有遮挡/误点；Classic 基线没有变化；常见咨询没有无关工具流程；错误有恢复入口；安全说明仍准确；报告中列出的行为都有修复后的证据。
